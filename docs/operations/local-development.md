# Local Development — Dekolife Platform

**Purpose:** How to run, reset, test and build the stack on a developer machine, using containers only, plus the one-command wrapper contract and the Windows-host specifics.
**Audience:** Every engineering agent, the reviewer, the client's technical team after handover.
**Status:** Baseline v1 (Phase 0). Verified against the pinned stack in `docs/canonical-context.md` §2 (PHP 8.4, Laravel 13.x, MySQL 8.4, Livewire 4, Tailwind 4, Vite).
**Source:** Stack and conventions: `docs/canonical-context.md` §2, §7. Contract obligations served by this environment: `پیوست ۱` بند ۱ (Laravel + MySQL, modular), `پیوست ۱` بند ۹ (daily backup — the same dump command is used locally), `ماده ۴` بند ۳ (tests must actually run), `پیوست ۱۰` بند ۶ (install documentation is a handover item).

## 1. Prerequisites

| Requirement | Minimum | Check |
|---|---|---|
| Docker Engine / Docker Desktop (WSL2 backend on Windows) | 24.x, Compose v2 | `docker version`, `docker compose version` |
| Git | 2.40+ | `git --version` |
| Free ports | 8080, 3306, 8025, 1025, 5173 | `docker compose ps` after `up` |
| Disk | 8 GB free (images + MySQL volume) | `docker system df` |
| PHP / Composer / Node on the host | **not required and not supported** | — |

There is **no PHP on the host** and that is deliberate: the runtime, the test database and the asset toolchain all live in containers, so "works on my machine" and CI cannot diverge. Every command below goes through Docker.

## 2. Services

`compose.yaml` at the repository root defines exactly four services (per `docs/canonical-context.md` §2):

| Service | Image / build | Container port | Host port | Role |
|---|---|---|---|---|
| `app` | `docker/php/8.4-fpm` (build) | 9000 | — | PHP-FPM 8.4, Composer, Node 22, `artisan`, queue worker, scheduler |
| `nginx` | `nginx:1.27-alpine` | 80 | **8080** | web entry point, serves `public/`, proxies to `app` |
| `mysql` | `mysql:8.4` | 3306 | **3306** | primary database `dekolife`, test database `dekolife_test` |
| `mailpit` | `axllent/mailpit` | 1025 (SMTP), 8025 (UI) | **1025**, **8025** | catches all outbound mail in development |

Optional profile `assets` adds a `vite` service on **5173** for hot reload. It is a profile, not a fifth default service, so `docker compose up -d` stays the four-service baseline.

**URLs**

| What | URL |
|---|---|
| Storefront | http://localhost:8080 |
| Admin panel | http://localhost:8080/admin |
| Mail catcher (all dev mail lands here) | http://localhost:8025 |
| Vite HMR (only with `--profile assets`) | http://localhost:5173 |
| Health probe | http://localhost:8080/health/ready |

**Database defaults (development only, never reused in staging or production)**

| Key | Value |
|---|---|
| database | `dekolife` (tests: `dekolife_test`) |
| user / password | `dekolife` / `dekolife` |
| root password | `root` (container-local only) |
| charset / collation | `utf8mb4` / `utf8mb4_0900_ai_ci` |
| timezone | UTC in the container; display timezone `Asia/Tehran` in the app |

These values live in `.env` (untracked). `.env.example` carries the same keys with the same development defaults so a fresh clone works without editing anything except `APP_KEY` (generated by `scripts/dev up` if missing).

## 3. First run

```bash
git clone <repository-url> dekolife-platform
cd dekolife-platform
cp .env.example .env                     # only if .env is absent
docker compose up -d --build             # builds app, starts all four services
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate --seed
docker compose exec app npm ci && docker compose exec app npm run build
docker compose ps                        # all four services "running"/"healthy"
```

Then open http://localhost:8080. Seeded accounts are created by `DatabaseSeeder` with the password from `SEED_DEFAULT_PASSWORD` in `.env` and are listed in the seeder's console output; the seeder refuses to run when `APP_ENV=production`.

**Wait for MySQL, don't guess.** The `app` container's entrypoint waits for TCP 3306 and the `healthcheck` on `mysql` uses `mysqladmin ping`; `docker compose up -d --wait` is the reliable form. If migrations fail with "connection refused", MySQL was not ready — re-run the migrate command, do not recreate the volume.

## 4. Everyday commands

| Task | Command |
|---|---|
| Start / stop | `docker compose up -d` · `docker compose down` |
| Stop and wipe the database volume | `docker compose down -v` |
| Shell in the app container | `docker compose exec app bash` |
| Any artisan command | `docker compose exec app php artisan <command>` |
| Migrate | `docker compose exec app php artisan migrate` |
| Migrate + seed | `docker compose exec app php artisan migrate --seed` |
| **Reset the database** | `docker compose exec app php artisan migrate:fresh --seed` |
| Run the test suite (real MySQL) | `docker compose exec app php artisan test` |
| One test file | `docker compose exec app php artisan test tests/Feature/Orders/PlaceOrderTest.php` |
| One test by name | `docker compose exec app php artisan test --filter=place_order_is_idempotent` |
| Style check / fix | `docker compose exec app ./vendor/bin/pint --test` · `./vendor/bin/pint` |
| Static analysis | `docker compose exec app ./vendor/bin/phpstan analyse --memory-limit=1G` |
| Rebuild assets | `docker compose exec app npm run build` |
| Watch assets | `docker compose --profile assets up -d vite` then `docker compose logs -f vite` |
| Queue worker (foreground) | `docker compose exec app php artisan queue:work --queue=default,notifications --tries=3 --timeout=90` |
| Scheduler (foreground, dev) | `docker compose exec app php artisan schedule:work` |
| Logs | `docker compose logs -f app` · `docker compose logs -f nginx` · `docker compose logs -f mysql` |
| MySQL shell | `docker compose exec mysql mysql -udekolife -pdekolife dekolife` |
| MySQL as root | `docker compose exec mysql mysql -uroot -proot dekolife` |
| Mail | open http://localhost:8025 |
| Queue depth | `docker compose exec app php artisan queue:monitor default,notifications --max=100` |
| Failed jobs | `docker compose exec app php artisan queue:failed` |

**Queue and scheduler run inside the `app` container**, not as separate services, so the compose file stays the canonical four. In development start them foreground in their own terminal; in production the same commands run under supervisor — see `runbooks.md` §1 and §4.

## 5. Resetting and seeding

| Need | Command | Effect |
|---|---|---|
| Schema + reference data | `php artisan migrate:fresh --seed` | drops all tables, re-runs migrations, seeds roles, categories, sample products, gateway sandbox config |
| Reference data only | `php artisan db:seed` | idempotent seeders only (roles, permissions, categories, settings) |
| Demo dataset for a demo or UAT dry run | `php artisan db:seed --class=DemoDatasetSeeder` | 10k products, 200 stores, 50 marketers, 500 orders, 30 days of invoices — takes ~3 minutes |
| Only the catalog import | `php artisan catalog:import --path=storage/app/import/products.xlsx` | idempotent, re-runnable, logs row-level rejects |
| Test database only | `php artisan test` (the suite migrates `dekolife_test` itself) | never touches `dekolife` |

Seeders must be **idempotent** (`updateOrCreate`, no blind `insert`), because `scripts/dev fresh` and the acceptance environment both re-run them. A seeder that fails on a second run is a bug, not an inconvenience.

## 6. One-command wrapper contract

`scripts/dev` is the only entry point an agent needs. It is a POSIX shell script (runs under Git Bash on Windows) that wraps `docker compose`. Target path: `scripts/dev`, created in Phase 0.

**Contract**

| Property | Requirement |
|---|---|
| Invocation | `scripts/dev <verb> [args…]` |
| Verbs | `up`, `down`, `restart`, `status`, `shell`, `art`, `test`, `pint`, `stan`, `fresh`, `build`, `watch`, `worker`, `scheduler`, `logs`, `db`, `backup`, `doctor` |
| Passthrough | `scripts/dev art migrate --seed` runs `php artisan migrate --seed` inside `app`; unknown verbs are rejected with the verb list and exit code 2 |
| Idempotency | `up` is safe to run repeatedly; it builds only when the image is missing or `docker/` changed, generates `APP_KEY` if absent, waits for MySQL health, and runs pending migrations |
| No host tooling | the script never invokes `php`, `composer`, `node` or `npm` on the host; if it detects `php` on PATH it warns once and ignores it |
| Exit codes | `0` success · `1` runtime failure · `2` usage error · `3` dependency missing (Docker not running) |
| Output | one line per action, prefixed with the service name; failures print the failing command and the last 40 log lines |
| Side effects | only inside the repository and named Docker volumes; never writes outside the working tree except the Docker volume |
| `doctor` | verifies Docker daemon, compose version, port availability, `.env` presence, `APP_KEY`, storage writability, MySQL reachability, Node version — and exits non-zero listing what to fix |

**Behavioural requirements that make it worth having**

- `up` must be the entire onboarding: a fresh clone plus `scripts/dev up` must produce a working storefront. This is a Phase 0 exit criterion and is re-tested before every release tag.
- `test` runs Pint `--test`, PHPStan and the full suite in that order, so a DoD check is one command.
- `fresh` prints a warning and requires `--yes` when `APP_ENV` is not `local`.
- `backup` calls the same `mysqldump` invocation documented in `backup-and-restore.md` §2, so the local drill and the production job cannot drift.

## 7. Windows host notes

The developer host is Windows 11 with Git Bash (MSYS). These are the failure modes that cost time, and their fixes.

| Symptom | Cause | Fix |
|---|---|---|
| `php: command not found` | by design — no host PHP | use `scripts/dev art …` or `docker compose exec app php artisan …` |
| `artisan` receives `/some/path` rewritten to `C:/Program Files/Git/some/path` | MSYS path conversion on arguments beginning with `/` | prefix the command with `MSYS_NO_PATHCONV=1`, e.g. `MSYS_NO_PATHCONV=1 docker compose exec app php artisan route:list --path=/api` |
| `the input device is not a TTY` on `docker compose exec` | Git Bash has no TTY for the child process | add `-T`: `docker compose exec -T app php artisan test`, or run the command from Windows Terminal |
| Interactive prompts never accept Enter | CR is required, a bare LF is not delivered | prefer non-interactive flags (`--force`, `--no-interaction`); avoid REPLs through the wrapper |
| File changes not visible in the container, or very slow | bind-mount performance on the Windows filesystem | keep the repository on the same drive as Docker's WSL2 backend; exclude the project from Windows Defender real-time scanning; if the suite is still slow, clone inside the WSL filesystem and open it from Windows via `\\wsl$` |
| `storage/` or `bootstrap/cache` not writable | host UID/GID differs from the container user | `docker compose exec app chown -R www-data:www-data storage bootstrap/cache` (the wrapper does this in `doctor --fix`) |
| Every file shows as modified after clone | CRLF line endings | `.gitattributes` sets `* text=auto eol=lf`; run `git config core.autocrlf false` once |
| Port 3306 already in use | a local MySQL/MariaDB service | change the host side only: `MYSQL_HOST_PORT=3307` in `.env`, then connect on 3307; container-internal 3306 is unchanged |
| Containers start but nginx returns 502 | `app` container not healthy yet | `docker compose logs app`; wait for the entrypoint's readiness line, then reload |
| Case-only filename collisions (e.g. `Catalog` vs `catalog`) | Windows filesystem is case-insensitive, Linux is not | never create two files differing only by case; CI on Linux catches it, local runs do not |

**Do not** install PHP, Composer or MySQL on the host to "make things simpler". A host PHP that differs from 8.4 silently produces different behaviour than CI, and every bug hunt then starts with an environment argument.

## 8. Test environment rules

- Feature and integration tests run against **MySQL 8.4**, never SQLite (`docs/canonical-context.md` §2). SQLite hides JSON, collation and transaction differences that matter for money and Persian text.
- The test database is `dekolife_test`, created by the `mysql` container's init script. `phpunit.xml` sets `DB_DATABASE=dekolife_test`, `CACHE_STORE=array`, `QUEUE_CONNECTION=sync`, `MAIL_MAILER=array`, and fake SMS/WhatsApp drivers.
- Pest parallel testing is **off by default**: parallel workers would share one MySQL schema. If it is enabled, each worker gets its own database (`dekolife_test_1..n`) and the CI job must create them.
- Tests may not depend on seeded demo data; each test builds its own fixtures. The only exception is reference data (roles, permissions) loaded by a test bootstrap seeder.
- A test that passes only when run alone is a defect: the suite runs in file order in CI, and ordering-dependent tests are rejected in review.

## 9. Troubleshooting

| Problem | Diagnosis | Resolution |
|---|---|---|
| Image build fails on `composer install` | network or a stale lock file | `docker compose build --no-cache app`; check `composer.lock` is committed |
| Migrations fail with a duplicate-table error | partially applied migration after a crash | `php artisan migrate:status`, then `migrate:fresh --seed` locally (never in staging/production) |
| `php artisan test` cannot connect | MySQL container unhealthy, or wrong `DB_HOST` | `docker compose ps`; `DB_HOST=mysql` inside the network, `127.0.0.1` only from the host |
| Assets 404 after a pull | manifest from an older build | `docker compose exec app npm run build` |
| Emails never arrive | mail is intentionally captured, not delivered | look in Mailpit at 8025 |
| Queue jobs pile up | worker not running | start it per §4; in CI, `QUEUE_CONNECTION=sync` means this only happens locally |
| Permission errors after switching branches | cached views/compiled files owned by another UID | `docker compose exec app php artisan optimize:clear` then re-chown |
| Timezone confusion in Jalali display | storing local time instead of UTC | store UTC, convert at presentation; a test asserts the stored value is UTC |

## 10. What "working locally" must prove

Before any release tag, on a machine that has never seen the project:

1. `git clone` → `scripts/dev up` → storefront loads, admin loads, mail arrives in Mailpit.
2. `scripts/dev test` green, including the MySQL-backed feature suite.
3. `scripts/dev fresh --yes` → `scripts/dev up` → the demo dataset seeds and the golden path can be clicked through.
4. `scripts/dev backup` produces a dump that `backup-and-restore.md` §4 can restore.

If any of the four fails, the release is not ready regardless of CI status — this is the local half of DoD point 5.
